# AI routing, jobs and notifications

## Credentials and discovery

All API credentials are server environment variables. On 2026-09-16, the owner explicitly authorized installing the previously supplied MaxPlus keys. Live discovery found nine Claude models and six GPT models. `gpt-5.6-sol` passed text, synthetic-vision, and every structured task-schema check, and is the active model for all five tasks. `claude-haiku-4-5-20251001` passed the narrow text/color checks but refused the domain-specific structured nutrition prompt, so it is intentionally not routed. The supplied China key duplicates the GPT key and is also not routed as an independent fallback.

Configure each pool independently using `AI_CLAUDE_*`, `AI_GPT_*`, `AI_CHINA_*` in `.env.example`. `BASE_URL` includes `/v1`; `PROTOCOL` is `messages`, `responses`, or `chat`. Defaults reflect the supplied integration notes and remain subject to per-key verification. Keys and upstream error bodies are never rendered, persisted in request logs, or exported. Restart web and worker after changing secrets.

In **Coach → AI models and routing**, discover each configured pool (`GET /models`), select a model and run its explicit text test. Food models additionally require a synthetic image color test. These admin actions make live requests and may consume credit. Discovery does not infer vision support from a model name or image-generation support. Models missing from a refreshed list lose availability and verification. Configure up to three verified models separately for Food Vision, Workout Analysis, Body/Progress Analysis, Daily Summary and Coach Chat. There are no automatically chosen model names.

Each logical request attempts each configured candidate at most once, up to three total. Requests use an 8-second connect timeout and 45-second network timeout. Authentication, credit, rate-limit, model-unavailable, network and upstream service failures allow fallback. Known model/vision incompatibility error codes revoke the corresponding availability flag. Ordinary malformed input and invalid structured output stop immediately for review. Request records retain only task, provider/model, sequence, latency and a fixed status code. The Coach screen shows attempts, fallback and a manual Retry button after all candidates fail. Retry is an explicit new execution of that job; it does not create duplicate successful analyses.

## Context and safe changes

Every output is validated against a task-specific Pydantic JSON schema; unknown fields, invalid ranges and nonfinite nutrient values are rejected. Suggested changes are additionally checked for target bounds and valid owned exercise references. No text response can execute an action. Only explicit Accept creates an immutable target/plan version inside a transaction; it checks both the expected version and exact before values. Reject records the decision without changing the active version. Stale proposals require fresh analysis. AI calorie proposals below 1,200 kcal or reductions over 20% are rejected; this is a guardrail, not individualized medical advice.

Context includes local-date windows of 1/7/14/30 days, same-source body readings, recent completed sets and effort, available equipment, sleep and cardio. Nutrition averages use **logged days only**, disclose sample count and window size, and do not equate unlogged days with fasting. Logged days can still be partial. Food retrieval matches note/name tokens against the full confirmed library before selecting at most 20 rows, so an older recurring food can be retrieved. Explicit notes and confirmed values outweigh image guesses. Food output stays editable; a snapshot prevents delayed analysis overwriting user corrections.

Context bounds: 120 body readings, 12 sessions with 60 sets each, 60 equipment names, up to 150 owned exercise references and 30 cardio entries; large workout history is reduced to meet a 48,000-character aggregate budget. Plans above 16,000 characters are represented as truncated metadata, and plan suggestions from such a context are rejected rather than comparing an incomplete before value. Food requests send resized JPEG data only, never a storage path. Logs and push messages contain no nutrition or health text.

## Durable jobs and schedule

Run `python manage.py runworker`; `--once` executes one maintenance/claim cycle for operational smoke checks. Every 5 minutes maintenance checks schedules/trends and photo retention. Idle jobs are polled every 30 seconds. Default summaries deduplicate by user and local calendar date, after the profile's configured summary time. **End Day** uses the same date key. **Re-analyze Today** creates another job and a new analysis version. Changing a timezone affects future scheduling. Missed older days are not automatically backfilled.

Workers use compare-and-swap claims and an 8-minute lease; interrupted leases may be reclaimed, with three executions maximum before manual retry. A fenced transactional completion ensures only the current claim can persist output; output and all suggestions commit together. External requests may repeat after a worker crash, so upstream billing cannot be guaranteed exactly once. Daily output versions and successful job output are protected from duplicate persistence.

Default trigger rules are configurable: at least 6 same-source readings spanning 7 days, comparing first/last halves, with 2% weight change or 2 body-fat percentage points; at least 5 sleep observations in 7 days averaging below 6 hours; or consecutive estimated working-set performance decreases over 5% across 3 sessions of the same exercise. Performance is load × (1 + reps/30), used only as a coarse review trigger; AI receives actual effort/history to interpret it. Environment overrides are listed in `.env.example`. Triggered body/recovery jobs deduplicate to one per local day. The scheduled rule pass also detects sleep/performance changes; individual body saves run the rule layer without unconditional AI calls.

## Push

Generate a fresh VAPID key pair and configure `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, and a real contact `VAPID_SUBJECT`. Only the public key is sent to the browser. Enable notifications with explicit browser permission over HTTPS; iOS requires installation to the home screen. Subscriptions and revocations use authenticated CSRF-protected POST requests. Endpoints are restricted to official FCM, Mozilla and Apple push service hosts on HTTPS port 443. Delivery removes expired 404/410 subscriptions. Notifications only say a summary or suggestion is ready. Browser delivery requires a live device smoke test; mocked tests cannot establish permission or actual delivery. Subscription endpoints/keys are excluded from portable exports and must be registered again after migration.
